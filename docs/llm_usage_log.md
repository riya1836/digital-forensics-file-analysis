# LLM Usage Log

## 1. Overview

Large Language Model (LLM) assistance was used during the development of the **Digital Forensics File Analysis** project for system design, project structure, implementation support, debugging, testing, performance analysis, and documentation.

The project was divided into four major milestones:

- **M1 – File Scanning and Metadata Extraction**
- **M2 – Sequential Analysis**
- **M3 – Parallel Analysis using OpenMP**
- **M4 – Benchmarking and Performance Analysis**

The LLM was used as a development and problem-solving aid. The team reviewed, tested, modified, and validated the generated suggestions before incorporating them into the project.

---

## 2. System Design and Project Structure

LLM assistance was also used during the initial planning and organization of the project.

- Interpreted the project requirements and helped break the system into M1, M2, M3, and M4 modules.
- Helped define the data flow from file scanning to metadata generation, sequential/parallel analysis, and benchmarking.
- Helped design the project folder structure and identify suitable locations for source files, tests, datasets, outputs, results, scripts, and documentation.
- Helped determine the responsibilities and boundaries of each milestone so that the modules could be developed and tested independently.
- Suggested appropriate input/output relationships between modules, including the use of the M1 metadata CSV as input to M2 and M3.
- Provided guidance for organizing test files and benchmark results separately from source code.
- Helped identify the supporting scripts and documentation required for the complete project workflow.

---

## 3. M1 – File Scanning and Metadata Extraction

### Objective

M1 was responsible for recursively scanning the input dataset and extracting the metadata required by the later analysis stages.

### LLM-Assisted Activities

The LLM was used to:

- Interpret the project requirements and identify the exact scope of M1.
- Define the structure of the M1 implementation.
- Develop the initial structure for `file_analyzer.c` and `file_analyzer.h`.
- Implement recursive directory traversal.
- Extract file path, filename, extension, file size, modification time, file permissions, and hidden-file status.
- Implement CSV escaping and formatting.
- Handle files with missing extensions, hidden files, and modification-time formatting.
- Address POSIX/Linux/WSL compatibility issues.
- Provide compilation and execution guidance.
- Explain compiler warnings and runtime output.
- Clarify that M1 focuses on metadata extraction rather than analysis, scoring, or risk classification.

### Validation

The M1 implementation was compiled and executed successfully. The generated metadata CSV was subsequently used as input for the M2 and M3 modules.

---

## 4. M2 – Sequential Analysis

### Objective

M2 processes the metadata generated by M1 sequentially and performs file classification, scoring, and risk analysis.

### LLM-Assisted Activities

The LLM was used to:

- Review the M2 requirements and module contract.
- Define the input and output format: `intermediate/metadata.csv` and `outputs/sequential.csv`.
- Design structures for metadata records and analysis results.
- Implement extension-based categories: DOCUMENT, IMAGE, AUDIO, VIDEO, ARCHIVE, CODE, and OTHER.
- Implement file-size categories: SMALL, MEDIUM, and LARGE.
- Implement deterministic scoring based on file category, file size, hidden-file status, and owner-write permission.
- Implement LOW, MEDIUM, and HIGH risk classification.
- Correctly interpret Unix permission values as octal values.
- Implement robust CSV parsing, including quoted fields and fields containing commas.
- Implement safe CSV output formatting.
- Add execution-time measurement.
- Provide Ubuntu/GCC compilation and execution guidance.
- Design tests for file categories, size boundaries, hidden files, permissions, score calculation, risk labels, and record counts.
- Inspect generated output and maintain consistency with the parallel implementation.

### Validation

The M2 implementation was compiled and tested on Ubuntu/Linux. The output was inspected and used as the correctness reference for M3.

---

## 5. M3 – Parallel Analysis using OpenMP

### Objective

M3 performs the same analysis as M2 while using OpenMP to parallelize the processing of metadata records.

### LLM-Assisted Activities

The LLM was used to:

- Plan the parallel analysis module.
- Identify record-level data parallelism as the appropriate parallelization strategy.
- Implement the analysis using C and OpenMP.
- Use `#pragma omp parallel for` for parallel record processing.
- Preserve the same classification, scoring, and risk logic used by M2.
- Support configurable thread counts such as 1, 2, 4, and 8.
- Generate `outputs/parallel.csv`.
- Add parallel execution-time measurement.
- Design correctness checks comparing parallel and sequential results.
- Test the implementation with multiple thread counts.
- Provide Linux/Ubuntu OpenMP compilation guidance.
- Help interpret the effect of thread count on execution time.

### Validation

The M3 implementation was tested using multiple thread counts. Sequential and parallel results were compared to verify logical consistency, and record counts were checked across executions.

---

## 6. M4 – Benchmarking and Performance Analysis

### Objective

M4 experimentally evaluates the sequential and parallel implementations across different dataset sizes and thread counts.

### LLM-Assisted Activities

The LLM was used to:

- Interpret the M4 requirements and plan the complete benchmarking workflow.
- Design automated benchmarking for small, medium, and large datasets.
- Benchmark sequential execution and parallel execution using different thread counts.
- Organize raw benchmark measurements.
- Calculate execution time, speedup, and parallel efficiency.
- Design result-processing and comparison functionality.
- Compare sequential and parallel logical results using file paths rather than relying only on row order.
- Plan visualization of execution time, speedup, and efficiency.
- Analyze possible bottlenecks including OpenMP overhead, file I/O, scheduling overhead, synchronization, workload imbalance, insufficient computational workload, and hardware limitations.
- Assist with M4 testing and interpretation of benchmark results.
- Explain the complete M1 → M2/M3 → M4 workflow.

### Validation

The benchmark was executed using actual measured execution times. Speedup and efficiency values were calculated from the measured results, and graphs were generated from the benchmark data.

## 8. Human Verification and Responsibility

LLM-generated suggestions and code were treated as development assistance rather than automatically verified project results.

The team members were responsible for:

- Reviewing generated code and recommendations.
- Adapting implementations to the project requirements.
- Compiling the source code.
- Running the test cases.
- Inspecting generated outputs.
- Verifying sequential and parallel results.
- Running benchmark experiments.
- Checking measured performance results.
- Making final implementation and design decisions.
- Ensuring that the final project behavior matched the required specifications.

The final implementation and reported experimental results were validated through actual compilation, execution, testing, and benchmarking.
